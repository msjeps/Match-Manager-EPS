- **Dépôt distant** : github.com/msjeps/Match-Manager-EPS (renommé depuis msjeps/TEN-EPS le 2026-08-02, GitHub redirige l'ancienne URL), déployé sur https://apps.outils-eps.fr/TEN-EPS/ via GitHub Pages (branche `main`, racine `/`) — **URL technique pas encore reconfigurée**, voir `TODO.md`.
- **Fichiers suivis par git** : `index.html`, `icon_192.png`, `icon_512.png`, `logo-outils-eps.png`, `manifest.json`, `sw.js`. Tout le reste (`CLAUDE.md`, `MatchManagerEPS.apk`, `android/`, `design_preview.html`, `.claude/`, `.DS_Store`) est dans `.gitignore` — dev-only, jamais poussé.
- **App compagnon** : [SCAN EPS](file:///Users/nathalieprenois/AndroidStudioProjects/SCAN%20EPS) scanne le QR code des résultats généré par Match Manager EPS (préfixe technique inchangé `TENEPS|`, comparaison de chaîne exacte côté SCAN EPS). Compatibilité vérifiée pour les modes 1/2/3 le 2026-08-02.

## Décisions & historique

### 2026-08-02 — Renommage exécuté : TEN EPS → Match Manager EPS
Suite à la généralisation du format de match (voir décision ci-dessous), l'app n'était plus spécifique au tennis de table — le nom "TEN EPS" ne correspondait plus à ce qu'elle fait. Nathalie a choisi **"Match Manager EPS"** ("Tournoi EPS" étant déjà pris par d'autres apps existantes).
**Fait** : titre/`<title>`/logo/footer/aide (`index.html`), `manifest.json` (`name`/`short_name`/`start_url`), `README.md`/`CLAUDE.md`/`TODO.md` (projet), entrée dans le `CLAUDE.md` racine de la flotte (tableau + section), ressources `android/` (label, `strings.xml`, `settings.gradle` — dossier gitignoré, jamais buildé/poussé), fichiers locaux `TEN_EPS.html` → `MatchManagerEPS.html` et `TEN_EPS.apk` → `MatchManagerEPS.apk`, dossier projet `TEN EPS` → `Match Manager EPS`, dépôt GitHub `msjeps/TEN-EPS` → `msjeps/Match-Manager-EPS` (+ remote `origin` local mis à jour). En profité pour corriger un bug préexistant signalé au TODO : `sw.js` (`ASSETS`/fallback) et `manifest.json` (`start_url`) référençaient encore `./TEN_EPS.html`, un fichier gitignoré donc absent du site déployé — pointent maintenant vers `./index.html`, le fichier réellement servi. `CACHE_NAME` bumpé en conséquence.
**Volontairement inchangé** : le préfixe technique du payload QR (`TENEPS|`, lu par SCAN EPS via comparaison de chaîne exacte) et la clé localStorage (`teneps_data`) — casser l'un ou l'autre romprait la compatibilité avec SCAN EPS ou perdrait les données déjà sauvegardées sur les tablettes.
**Reste à faire** (voir `TODO.md`) : nouveaux logos `icon_192.png`/`icon_512.png` (Nathalie les refait), reconfiguration côté hébergeur de l'URL `apps.outils-eps.fr/TEN-EPS/` (hors de portée d'un agent Claude Code).

### 2026-08-02 — Généralisation du format de match (score/temps)
L'app peut se généraliser à d'autres activités (badminton, volley, basket, foot, hand, rugby...), y compris par équipes. L'ancien réglage `T.settings.format` (`set11`/`set21`/`bo3`) pilotait la saisie du score, la validation ("pas de match nul" en dur) et le calcul du classement — pas qu'une étiquette.
**Solution retenue** : deux familles de format au choix par tournoi — `matchFamily:'score'` (manches gagnantes 1/2 × points par manche 11/15/21/25, remplace `winningSets`/`pointsPerSet` l'ancien `isBo3`) et `matchFamily:'time'` (nombre de périodes 2/3/4 × durée par période uniforme, matchs nuls autorisés avec un nouveau réglage `drawPts`). Migration automatique et non destructive des anciens tournois via `migrateSettings()` (appelée dans `load()`).
Le classement (`calcPoolRanking`/`renderOverallRanking` mode 2/`downloadCSV` mode 2) était dupliqué 3× avec une logique qui ne gérait aucune égalité — extrait dans un helper partagé `statsFromMatches()` qui ajoute la branche match nul. La phase bracket (mode 3) reste strictement sans match nul (garde-fou explicite dans `validateMatch`), car `resolveEntry`/`resolveLoser` ne gèrent aucune égalité pour l'avancement du tableau — ne jamais leur exposer un match nul.
Vérifié : migration d'anciens tournois, création d'un tournoi "au temps", match nul accepté en poule et rejeté en bracket, classement avec colonne "N" correcte, export XLSX sans erreur, QR payload inchangé et toujours compatible avec [SCAN EPS] (les nuls n'incrémentent ni `w` ni `l`, donc la forme du payload ne change pas).
Reste à faire (Partie B, voir `TODO.md`) : chronomètre actif par match pour le format "au temps" (start/pause par période, sonnerie, plusieurs matchs simultanés, Wake Lock — l'app n'a aujourd'hui aucune API Wake Lock, à créer de toutes pièces).

### 2026-08-02 — QR code et export visibles sur l'écran Classements
Avant, le QR code des résultats n'était accessible que via l'icône en haut à droite (menant à l'écran Export). Or dans toutes les autres apps EPS de la flotte, ce coin est réservé aux réglages/aide — donc masquer le QR derrière cette icône était incohérent avec les habitudes de l'utilisatrice.
**Solution retenue** : QR code + bouton "Télécharger XLSX" ajoutés directement sous le tableau de classement (`scr-rankings`), via une fonction partagée `renderQRCode(containerId)` réutilisée aussi par l'écran Export. L'icône du coin supérieur droit reste disponible pour l'export complet (résumé + XLSX), sans changement de comportement.
Validé sur les 3 modes de tournoi (poules, poules+finales, bracket) sans erreur console.

### 2026-08-02 — Mise en place du dépôt git local
Le dossier local n'était pas un dépôt git alors qu'un dépôt distant existait déjà (historique + fichiers de déploiement `index.html` etc.). Plutôt que de créer un nouvel historique (et risquer un force-push destructeur), le dépôt local a été rattaché à l'historique existant (`git fetch` + `checkout -b main origin/main`). Les icônes/manifest/sw.js locaux étaient déjà identiques à ceux du dépôt distant.

### 2026-08-02 — Audit sécurité/qualité + correction XSS stockée et ajout du mot de passe admin
Audit complet demandé par Nathalie. Deux failles confirmées et corrigées (commit `12520e8`) :
- **XSS stockée** : les noms de joueurs, le nom du tournoi, la classe et les noms de listes sauvegardées étaient des champs texte libres réinjectés tels quels dans `innerHTML` à une quinzaine d'endroits (accueil, liste joueurs, distribution, cartes de match, dropdown arbitre, classements poule/général/bracket, chips têtes de série/exemptions, résumé export, modale listes sauvegardées). Un nom du type `<img src=x onerror=...>` exécutait du JS arbitraire dès l'affichage — risque concret vu la contrainte RGPD de la flotte (`CLAUDE.md` racine : « aucune sortie de la tablette ») si la tablette repasse en Wi-Fi hors cours. La fonction `escX()` existante ne protégeait que l'export XLSX (échappement XML), jamais le rendu HTML. **Solution** : nouveau helper global `escH()` ([MatchManagerEPS.html:492](MatchManagerEPS.html:492)) appliqué à tous ces sites. Les noms de poule et de finale ne sont pas concernés : ils sont générés par l'app (« Poule 1 », « Finale des 1ers »...), jamais saisis par l'utilisateur. Le rendu SVG du tableau (bracket visuel) était déjà protégé via `escSvg()`, inchangé. Vérifié dans le navigateur avec des payloads réels (`<img onerror>`, `<svg onload>`) sur tournoi/classe/joueur : aucune exécution, aucune erreur console, jusqu'à l'écran d'accueil.
- **Correctif incomplet à l'origine** : la vérification initiale avait manqué `renderOverallRanking()` (onglet "Général ★" des classements, utilisé en mode 1 dès 2 poules et en mode 2) — deux `p.name` non échappés y subsistaient malgré la doc de ce commit annonçant les classements "poule/général/bracket" comme couverts. Trouvé par un code-review (agent `code-reviewer`) lancé après coup sur le diff, corrigé dans la foulée (mêmes lignes, `escH()`), revérifié par injection directe de payload dans `T` + appel de `renderOverallRanking()` en console (modes 1 et 2) : plus d'exécution. Leçon : quand une fonction de rendu est dupliquée (ici classement croisé vs classement par poule), vérifier chaque copie séparément plutôt que supposer qu'un pattern trouvé une fois s'applique partout.
- **Accès réglages sans protection** : l'icône ⚙ menait directement à `scr-admin` sans aucune vérification, alors que `DESIGN-SYSTEM-EPS.md` impose un accès prof protégé (référence Biathlon VMA). **Solution** : reprise fidèle du pattern Biathlon VMA — mot de passe par défaut `ADMINPROF` (jamais affiché en clair dans la modale de connexion, aide renvoyée vers le guide prof sur outils-eps.fr), mot de passe personnalisable stocké dans une clé localStorage dédiée `mmeps_admin_pwd` (séparée de `teneps_data`, donc non affectée par « Supprimer toutes les données »), et bouton de réinitialisation à `ADMINPROF` après 3 échecs consécutifs avec mot de passe personnalisé actif. Vérifié dans le navigateur : `ADMINPROF` donne accès par défaut, refusé une fois un mot de passe personnalisé enregistré, le bouton de réinitialisation apparaît au 3e échec et redonne l'accès via `ADMINPROF`. La confirmation JS (`confirm()`) du bouton de réinitialisation est auto-rejetée par le navigateur de test automatisé (dialogues natifs désactivés) — le chemin de code a été vérifié indépendamment (suppression directe de la clé) mais pas le clic réel sur la boîte de dialogue ; à revalider sur tablette avant diffusion aux élèves.

**Reste à faire** (non corrigé, à traiter dans une prochaine session — voir aussi `TODO.md`) : `CLAUDE.md` du projet décrit encore un export CSV alors que le code génère un vrai XLSX (générateur ZIP/OOXML fait main) ; le titre/`manifest.json` disent toujours « Tennis de Table » alors que l'app a été généralisée à d'autres sports.

### 2026-08-02 — Correction des non-conformités matérielles relevées à l'audit
Suite de l'audit ci-dessus : les 4 points classés « non-conformité matérielle » ont été corrigés.
- **`linear-gradient`+`border-radius` combinés** : piège documenté dans le CLAUDE.md racine, déjà rencontré sur LaserFit (Score Total invisible sur PowerVR GE8320). Trois règles CSS combinaient les deux propriétés sur le même élément : `.btn-primary` ([MatchManagerEPS.html:30](MatchManagerEPS.html:30), le bouton d'action principal de tout l'écran), `.player-item .num` (badge numéro circulaire) et `.progress-fill` (barre de progression). Les trois sont passées en couleur unie (`background:var(--pri)` / `var(--ok)`), conformément au pattern de référence Biathlon VMA qui n'utilise que des couleurs unies pour ses boutons. `.top-bar`, `.ranking-table th`, `.timer-bar` et le `.pool-header` (dégradé inline par poule) gardent leur `linear-gradient` : vérifié qu'aucun n'a de `border-radius` sur le même élément (le style arrondi de `.pool-card` vient d'un `overflow:hidden` sur le parent, pas d'un `border-radius` sur `.pool-header` lui-même), donc hors du périmètre exact du bug documenté — non touchés.
- **Orientation verrouillée** : `manifest.json` passait `"orientation":"portrait"` → `"orientation":"any"`, conforme à l'exigence « Libre (portrait + paysage) » du CLAUDE.md racine et du projet.
- **`requestFullscreen()` absent** : ajouté (`requestAppFullscreen()`, avec préfixes vendeur `webkit`/`moz`/`ms`), déclenché sur le premier clic/tap de l'utilisateur via `document.addEventListener('click', ..., {once:true})` — l'API exige un geste utilisateur, elle ne peut pas être appelée au chargement.
- **Wake Lock incomplet** : n'était acquis que pendant un chrono de match actif (format « au temps »), jamais pendant la saisie de score simple (format « au score », l'usage majoritaire). Découplé des chronos : `ensureWakeLock()` est maintenant appelé une fois à l'initialisation de l'app et réacquis sur `visibilitychange` (retour au premier plan) sans condition sur l'état des chronos. Le verrou n'est plus jamais relâché manuellement (fonction `releaseWakeLockIfIdle()` et ses 4 points d'appel supprimés) — seul le navigateur le relâche automatiquement quand l'onglet passe en arrière-plan, ce qui est le comportement voulu.

Vérifié dans le navigateur : `getComputedStyle(...).backgroundImage` confirme `none` sur `.btn-primary` (couleur unie effective) ; `requestAppFullscreen`/`ensureWakeLock` bien définies et appelées ; aucune erreur console. Le navigateur de test automatisé de ce workspace refuse par politique la permission Fullscreen (`Permissions check failed`) et Wake Lock (`NotAllowedError: Wake Lock permission request denied`) — comportement de sandbox, pas un bug : le code utilise l'API standard avec gestion d'erreur silencieuse (`.catch()`), comme le faisait déjà le Wake Lock du chronomètre avant cette session. **À revalider sur une vraie tablette** (voir `TODO.md`) : disparition effective de la barre de statut/navigation après le premier tap, écran qui ne s'éteint plus pendant une saisie de score simple.

### 2026-08-02 — Mode clair (dernier point « design system » de l'audit)
`DESIGN-SYSTEM-EPS.md` demande un `body.mode-sombre` avec surcharge systématique de chaque composant coloré. Mais **Match Manager EPS est nativement en thème sombre** (`:root{--bg:#213364;--txt:#FFFFFF;...}`) — contrairement à Biathlon VMA (référence du design system, clair par défaut) et à VB EPS (`:root` clair, `body.dark` en surcharge). Le point d'audit « pas de mode sombre » était donc mal posé : ce qui manque ici, c'est l'inverse, un **mode clair**.
**Précédent trouvé dans la flotte** : VB EPS n'implémente son `body.dark` qu'en surchargeant 6 variables CSS neutres (`--bg`,`--card`,`--text`,`--text2`,`--border`,`--shadow`) — pas composant par composant comme le texte du design system le suggère littéralement (Biathlon, lui, n'utilisant pas de variables CSS, a besoin de ~50 règles `.mode-sombre .composant`). Comme Match Manager EPS est déjà architecturé à 95% autour de variables CSS (`--pri`,`--bg`,`--surf`,`--surf2`,`--txt`,`--txt2`,`--brd`,`--sh`...), le précédent VB EPS s'applique directement ici : une seule surcharge de variables suffit pour la quasi-totalité de l'UI.
**Solution retenue** : `body.light-mode` surcharge `--bg`,`--surf`,`--surf2`,`--txt`,`--txt2`,`--brd`,`--sh`. `--pri`/`--accent`/`--ok`/`--err` (couleurs d'accent) restent identiques dans les deux thèmes, comme le fait VB EPS pour `--primary` — un badge ou un bouton accentué reste lisible quel que soit le thème sous-jacent. La barre du haut et la barre de chrono du chronomètre (`.top-bar`,`.timer-bar`) utilisaient `var(--surf)`/`var(--surf2)` pour leur dégradé ; comme VB EPS garde sa `.topbar` à une couleur de marque constante dans les deux thèmes, ces deux barres ont été découplées vers deux nouvelles variables figées `--chrome1`/`--chrome2` (jamais surchargées par `body.light-mode`) au lieu de suivre le thème — elles gardent leur bleu marine de marque, seul le contenu (cartes, tableaux, formulaires) s'éclaircit.
Deux surbrillances `rgba(255,255,255,X)` codées en dur (zébrure du tableau de classement, ligne « bye » du bracket) auraient été invisibles sur fond clair — surchargées en `rgba(0,0,0,X)` via `body.light-mode .selecteur`. `.info-box` (texte `#BDD3FF` codé en dur) et le placeholder du champ nom joueur (`#f4eac5` codé en dur) auraient eu un contraste quasi nul sur fond clair — passés à `var(--txt2)`.
**Hors périmètre, assumé** : les teintes translucides `rgba(couleur-accent,alpha)` des badges/chips/états de carte de match (victoire/attente/en cours) ne sont pas retouchées par thème — comme VB EPS ne le fait pas non plus pour ses propres badges accentués. Elles restent lisibles (teinte pâle sur fond clair est un pattern courant), juste pas retravaillées au pixel près.
**UI** : toggle "☀️ Mode clair" dans une nouvelle carte "🎨 Affichage" de l'écran Paramètres, au-dessus de la carte mot de passe. Persisté dans `localStorage['mmeps_light_mode']` (clé séparée de `teneps_data`, même logique que `mmeps_admin_pwd`), appliqué à l'init via `applyLightMode()`.
Vérifié dans le navigateur : bascule clair/sombre en direct, préférence conservée après rechargement de page, écran d'accueil/joueurs/classements/Paramètres tous lisibles en clair (zébrure de tableau visible, placeholder du champ nom visible, texte de l'encart mot de passe lisible), barre du haut et barre de chrono restent bleu marine dans les deux thèmes, aucune erreur console.
